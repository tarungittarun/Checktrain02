# R174 · Mobile website access: request research and fail-closed Actions assurance

The selected source is **the independent `whereismytrain.org.in` HTML website**, not Google's Where Is My Train phone app, the distinct `.in` cache, or NTES. The user asked which mobile APK requests could avoid a refusal, and for an Actions simulation. There is no basis to assert that changing a User-Agent/TLS fingerprint or doing enough retries would obtain permission or stop a 403. We can control our client request discipline and test it; only the website operator can explain/approve its CDN/origin policy.

## Measured facts, not theories

- The site's public indexed train links use `https://whereismytrain.org.in/?trainNo=NNNNN`, matching the app. A prior HTML inspection found only `/api/search.php` **autocomplete**, not a documented dated running-status API. The original app sent a Chrome-like UA when both success and failure were observed on the owner's phone. The later honestly identified app, runner's Python request, real runner Chrome navigation and API34 installed-app selection all received 403/browser verification. The latest [English-negotiated installed-APK run 42215089125](https://github.com/tarungittarun/Checktrain02/actions/runs/42215089125) still failed the source-strict card/clock gate on an in-app HTTP 403. Header spelling, parser changes, or more time cannot turn a completed 403 into an authorized 200.
- [Hostinger's browser-verification guide](https://www.hostinger.com/support/hostinger-cdn-the-browser-verification-page/) says its JS check evaluates risk signals and issues a verification cookie to browsers that pass; it notes IP reputation, data-centre networks, attack protection and security level as *possible* triggers. This does **not** identify the specific rule on this domain. We did not try to solve the check, replay a cookie, spoof Android Chrome or rotate IP addresses.
- [Hostinger's blocked-legitimate-requests guide](https://www.hostinger.com/support/hostinger-cdn-how-to-fix-blocked-legitimate-requests/) says the site owner can correlate URL, method, UTC timestamp and unredacted `x-hcdn-request-id` with its traffic blocking/security settings and support. `Server: hcdn` alone cannot distinguish CDN-generated from origin-generated 403. A precise provider-approved client/endpoint policy is preferable to lowering security globally. No provider approval or genuine-client HAR has been supplied here.

## Executable two-level Actions assurance

`.github/workflows/wimt-mobile-request-assurance.yml` is opt-in (`[wimt-assurance]` or manual dispatch) and sends **no GET to the independent website**. Its first job tests the app's request contract and real `Http` wire on an owned local server: 302, 403 and 429 must each generate exactly **one** GET with the honest headers, no cookie/authorization, no unprompted IPv4/status retry and no redirect follow-up. Existing parser tests exercise an accepted HTML *fixture* and exclude future/schedule-echo clocks. The second job installs the newly built APK + test APK into an **offline API34 emulator**, exercises production `PublicPageChecks` against test-owned 403 and 200 browser-check replies, verifies the host-wide pause, opens a train tracking screen, and requires a real in-app PNG plus matching hierarchy. This is a mobile-behavior simulation, **not** a website response.

The final, separate `live-source-verdict` job reads the latest completed [source-strict website device workflow](../.github/workflows/wimt-device-acceptance.yml). If that live run failed (as of 42215089125), or if either simulation job fails, this workflow is RED. Even if a live run becomes green, it downloads the *actual* live run artifact and requires accepted network transport, positive website GET receipt, qualified site rows, exactly one passed instrumentation method, and in-app screenshots. An expired/missing artifact is not a pass. No response body, raw cookie, challenge token or CDN ID is posted in the Actions comment. A green local scenario **never** upgrades live access. The owner-phone/provider permission requirement remains independent of this CI gate.
