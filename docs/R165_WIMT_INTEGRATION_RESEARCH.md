# R165 · WIMT source: integration research and release gate (2 November 2026)

**Outcome:** No new APK or claimed WIMT integration. PR #3 remains open. This is a decision record for getting *real* WIMT data into TrackTrain, not a substitute for it. The requested automatic Google phone-app data is not available through a verified, permitted contract in the evidence reviewed. The selected independent `.org.in` website is also currently refused on the owner's device. The actionable way forward is a provider-granted feed/exception with documented semantics, or a verified user-initiated share *if its real payload contains enough data*; neither is established by this research.

## 2. Request-forensics: is TrackTrain itself causing refusal?

Path: `PublicPageChecks.url(ORG)` builds `https://whereismytrain.org.in/?trainNo=<five-digit-number>` → `headersFor(ORG)` sets `Accept: text/html` → `Http.get` makes one HTTPS GET with identified `OpenTrackIndia/1.0` User-Agent, gzip, connection close and a four-second budget → `Http.tryOnce` checks the HTTP status **before** reading/parsing the page. A 403 returns `Failed(HTTP, "HTTP 403")` and R164 records bounded refusal metadata; it does not read the challenge body. `LiveViewModel` pauses that host for 15 minutes after a 403/429, retains the manually selected source as the next manual target and labels any NTES fallback separately. The three Refresh taps after the first R164 refusal produced **no new site GET**.

The R158 successful October 28 and R161 failed November 1 initial GETs had the **same Chrome-like User-Agent and same URL/transport**; R162 replaced that misleading UA with the honest app identity, removed HTTP-error retry/cache fallback and reduced unsolicited website checks; the November 2 phone still received 403 with `Server: hcdn`. The first November 1 GET was denied *before* its own later burst of follow-up requests, though that prior design (seven 403 GETs within ~33 seconds) was a real pacing defect worth correcting. We cannot tell from available diaries whether an earlier traffic pattern, IP reputation, site-wide protection, or a rule change triggered the first refusal. R164's redacted-upload CDN ID is **not** sufficient to ask the operator to find the specific request; only the original unredacted receipt would be.

Independent requests to the website return “Checking your browser before accessing”. Hostinger documents a JS verification and verification cookie for browsers; ordinary non-browser HTTP clients may not reach content [12](https://www.hostinger.com/support/hostinger-cdn-the-browser-verification-page/). Together with the phone's `hcdn` server header, this is strong CDN-gate evidence, **not proof of the site's exact mode or security rule**. Changing `Accept`, User-Agent, parser, TLS impersonation, WebView challenge-solving or replaying a browser cookie does not establish authorized app access. Do not deploy a challenge workaround. Hostinger's *site-owner* instructions are to inspect the blocked request's time/method/URL and `x-hcdn-request-id`, then review rules or request a precise exception [13](https://www.hostinger.com/support/hostinger-cdn-how-to-fix-blocked-legitimate-requests/). TrackTrain cannot change those site-owner settings.

## 4. Acceptance contract for any future authorized feed

1. **Identity:** response explicitly binds the five-digit train number to the correct run-origin day (IST); daily rollover and diverted/duplicate runs must not silently reuse yesterday's status. If the website omits a run day, visibly label timetable-based inference rather than authenticating it.
2. **Provenance:** classify each clock as schedule, source-reported station event, predicted/estimated, page publication, or cache retrieval. Require an explicit provider assertion that the event occurred, station code + event type (arrival/departure) + event time + meaningful observed/published age before admitting a source-reported actual; never turn an ETA, schedule or old `curStn` into a confirmed event or present train position.
3. **Route:** match station code and route order; handle intermediate/passing stations and overnight day2/day3. Reject wrong-direction, out-of-order or impossible time pairs (including departure before arrival). Do not overwrite existing NTES actuals with another source's comparison.
4. **Transport:** use the provider's documented identity/authentication and permitted frequency; one selected-source request before fallback; honor 403/429/Retry-After; no challenge automation, cache-as-fresh, parallel train-survey bursts or browser impersonation.
5. **Privacy/build:** no secrets in APK, screenshots or diary. If a key must be server-side, design an approved backend and request limit rather than embedding it in the Android package. Keep existing signing/update path; add golden provider fixtures and rejection tests without weakening current assertions.
6. **Evidence:** before claiming success, obtain written provider permission/contract and a provider-supplied sample; then an actual owner-phone **allowed network response** with the intended train/run, dated station rows and freshness; check table attribution and manual/auto behavior. CI passing alone is not phone success. Keep PR #3 open until the user confirms.

## 5. Decision today

No provider-granted feed, unredacted CDN correlation value or authentic Google-app share example is currently in the workspace. An additional speculative request/header tweak or APK would not make WIMT work and would risk a false success claim. The narrow next input is **either** (a) a written agreement/spec/approved CDN exception from the correct operator, **or** (b) a real, redacted, user-initiated share payload from the Google app (to evaluate a *manual import only*). These are different routes: a manual share cannot satisfy automatic Refresh. When the contract and example exist, implement against the gate above and validate on the owner's device; do not merge PR #3 beforehand.
