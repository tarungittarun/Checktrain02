# Source contract: `whereismytrain.org.in` train-status HTML

**Canonical reference for TrackTrain's selected “Where Is My Train · website” source.** Reviewed 19 Oct 2026 against branch `arena/6f68e526-checktrain02` (R139). This is **not** Google's Where is my Train phone app and **not** `whereismytrain.in/cache/live_status` (a separate web-cache candidate). Do not transfer a value between these three sources. In future discussions, start here rather than guessing what a “WIMT” response contains.

## Evidence boundary — what “whole response” can honestly mean here

- **OBSERVED**: bounded, real HTTP/HTML structural summaries for train **20689 on 15 Oct 2026**, preserved in the [c6348bf](https://github.com/tarungittarun/Checktrain02/commit/c6348bf) and [8bbf70b](https://github.com/tarungittarun/Checktrain02/commit/8bbf70b) commit comments and interpreted in [R101](../R101-website-run-and-intermediate-evidence.md). The bounded probe printed field counts, network-hook context, response size/hash/headers and selected card data; **it did not archive the full 91 kB HTML**. Owner device diaries/screenshots additionally show site reports for other trains; no raw 12089 HTML or complete HAR is present in this repository.
- **FIXTURE**: the synthetic HTML in `app/src/test/java/in/opentrack/india/v2/mirror/OrgWebsiteStatusTest.kt`, used to test parser decisions. An invented `1 km to ANF` in this fixture is *not* evidence that the real site prints such a field.
- **IMPLEMENTATION**: the exact data TrackTrain requests, parses and paints, inventoried below. This is a complete **app-side consumption inventory** for this source, **not** a byte-for-byte census of an unarchived live webpage. A field not in these summaries is **unknown**, not universally absent. The coding sandbox cannot connect to this website; this document does not claim a fresh 12089 network capture or discovered backend schema.

### Request variation ledger — what a changed field/signature actually established

| Variation | Evidence and decision |
| --- | --- |
| `trainNo=20689` | Supported by the captured train page and by the app's five-digit URL builder. Requesting another valid number selects that train's public page, **not** a new data type. |
| Add `date=2026-10-14` | **Already tried**, twice on 15 Oct for 20689. The old-date URL returned the **same visible station cards** as the undated URL at each comparison; extra bytes/hash changed because the URL was echoed. This does **not** select a historical run or establish a run date. See R101 and two commit comments. Do not infer that another date format works. |
| Search `q=…&type=…` | A `fetch('/api/search.php?q=…&type=…')` hook appears in the page's own frontend code. Its observed purpose is **search autocomplete**. It is not a dated status or next-km endpoint. The single `.json`/`/api/` tokens in the structural probe do not reveal a position API. |
| Change UA, Accept, cache headers, cookies, add `from`, `to`, `lang`, `appVersion`, signed params | **No evidence** these request a new field or enable position on this domain. Cache-control may affect intermediaries, never create provider telemetry. The extra `from`/`to`/`appVersion` style belongs to the **different `.in` web cache**, not this source; do not copy it or spoof a phone client. No undocumented credential/signature should be invented or bypassed. |

**Conclusion on “ask for extra fields”:** the only demonstrated train-status parameter here is `trainNo`. The proposed date parameter was tested and did not alter the visible run. The page's own identified secondary request is search, not status. No observed request field, header, signature or public client-side endpoint has been shown to produce next-station **remaining kilometres**. This is an evidence-based limit, not a claim that no backend anywhere could have them. Documented site UI/API or a legitimately obtained actual response showing a new field would be required before changing this contract; guessing query parameters is not a product plan.

## 2. Field-by-field response inventory and what TrackTrain does

**Key:** OBSERVED = historical site probe/owner evidence; FIXTURE = synthetic tests; CODE = parser supports it; UNKNOWN = not established by the evidence above. Static timetable/map inputs are explicitly **not website payload fields**.

| Payload part / finding | Evidence | App uses it for | App does **not** do with it |
| --- | --- | --- | --- |
| Visible train number plus `Source: <code>`, `Destination: <code>` | OBSERVED/CODE | Reject mismatched train/endpoints before interpreting any card. | Does not derive the run's origin **date**; app independently infers an active run from its dated timetable. Script/SEO matches are excluded. |
| Optional page-selected date text such as `Today`, `Selected date`, `Running status for` | CODE (conditional); 20689 trial had no accepted origin-date selector | Reject if explicitly printed date disagrees with requested origin date; otherwise describe run as inferred. | Does not turn a missing date into a site-confirmed date; adding `date=` to request was ineffective in 20689 trial. |
| Page status phrases (`yet to start`, `not running today`, `cancelled`, `diverted`, `reached destination`) | CODE | Header phrases indicating inactive/cancelled/diverted run block event admission; a completion phrase supplies status wording. | Generic heading/SEO “running” is not a measured position. |
| `Last Updated: hh:mm[:ss] AM/PM` | OBSERVED/CODE | Parse IST publication clock (seconds only if printed); reject missing, future or >5-minute-old page for a new report; show site page age separately and mark old badge stale. | Not a train event time, GPS tick or proof of motion. It changed with all 10 card groups unchanged in the real 20689 trial. HTTP `Date` is not substituted. |
| `<!-- Station Details Card -->`, `h3` station name/`(CODE)`, chronological card sequence, outer CSS classes | OBSERVED/CODE | Identify in-order route-matched cards. Green `bg-green-50 opacity-90` is past; blue `bg-blue-50` is considered only with a separately admissible past arrival; white/upcoming is not admitted. A card for an unknown or out-of-order station is skipped. | CSS “current” highlight alone cannot locate a moving train; future/white cards do not create actuals. Duplicate card data are not blindly merged. |
| Card `ARRIVAL`: first clock; second grey scheduled clock | OBSERVED/CODE | A past-marked first clock is admitted only if paired with a distinct second clock matching the selected static timetable within tolerance, chronologically plausible and no later than the page's **publication time**. Becomes an amber website-labelled arrival `WEB` in this source's right column. | The second clock is not a second event; a future ETA, schedule echo, lone first clock, or claimed event later than publication is rejected. Website claims are not independent NTES `Act`. |
| Card `DEPARTURE`: first clock; second grey scheduled clock | OBSERVED/CODE | Same gate; a settled earlier past card can show source-labelled departure. The latest reached card's departure, shown to drift with page clock in owner evidence, is **removed from settled rows** and kept separately as `provisionalDeparture`. A fresh/chronological provisional candidate can be rendered `WEB?` as **unconfirmed suggestion**. | Cannot copy latest revisable departure into `Act`, presume the train moved, or use a future estimate. Earlier actual departure from a different source is not the site's field. |
| `PF <platform>` on card | OBSERVED/CODE | Parsed from the card before arrival and displayed as `site pf` on eligible row; remains source-labelled. | Not a position, evidence of arrival, or substitute for a missing event clock. |
| Non-halt past cards e.g. BEI/SME (20689), repeated HTML cards | OBSERVED/CODE | If independently validated static map contains exact code in order with credible km, show website-marked past event and pin at **that named station**; latest event minute and age are retained. | Its static-map km comes from a **different** data source; never interpret as site-measured moving km or extrapolate after passing that point. |
| Visible `N km to CODE` | FIXTURE ONLY for R139's invented example; **not observed** in real 20689 summary or existing site-page fixture | R139 diagnostic scans **the same HTML** after site-report admission, strips scripts/styles, requires exactly one label, adjacent route point and remaining km within that validated span; reports an **unverified candidate** if present. | Does **not** move the train, fill actual times, prove source event time, or make another HTTP call. “Absent” only means this exact visible format was not found; differently formatted or hidden data remain unknown. |
| Three literal `distance` occurrences in real 20689 HTML; FAQ/SEO `NTES` mentions | OBSERVED | None for movement; inspected historically to avoid mistaking promotional “distance covered” prose for telemetry. | Does not represent next-station remaining km, an official NTES feed, a location coordinate, or an endorsed API. |
| Script/style/meta/ads, `fetch('/api/search.php…')`, generic `.json` token | OBSERVED/CODE | Intentionally strip scripts/styles before train identity and card text checks. Page SEO can mention other runs; diagnostic size/hash may include these bytes. | Do not mine SEO, ad code, scripts or autocomplete as today's live train position. |
| HTTP headers (`Date`, optional `Age`, caching, content encoding), local receipt clock | OBSERVED/CODE | Decode HTML, log request outcome/size/hash; show request time and stale-cache warning. | HTTP clocks and changing hashes are **not** event freshness. No assumed `Age` or cache-control response header is used as event time. |

## 3. Dataflow to UI — including negative paths

`TrainActivity` selection/Refresh → `LiveViewModel.probeSource(ORG)` → `PublicPageChecks.url/fetch` → shared `Http.get` → `PublicPageChecks.page` (visible comparison excerpts and optional date/status) → `OrgWebsiteStatus.parse` (validated `Report`) **and** R139 `OrgWebsiteDistanceProbe.inspect` (diagnostic only) → `LiveViewModel` per-source state → `WebsiteReportDisplay.rows` → `TrainActivity.bind` and `StopAdapter`.

- **Admission:** the timetable must match train/endpoints, weekday and one active origin-run window; website text must match identity/endpoints, page publication must be recent, cards must be past-marked/in-order, clock pairs plausible and not later than publication. Source answer plus rows is a *website comparison*; it never becomes independent official `primaryActuals` (`SourceEvidenceReceipt` writes `primaryActuals=0`, `primaryMarker=none`). Last report regressing to an older station cannot create backwards motion; a retained report keeps its original page/event clock.
- **Selected-source presentation:** amber `WEB` arrivals/settled departures on the right beside separate scheduled times; selected website headline, source badge with inferred-run warning, last site stop/intermediate, event age, site-at-stop delay against static schedule, next **scheduled** stop (not ETA). No report → schedule and explicit unknowns/fallback; a failed/cache-only reply cannot refresh an old event. A website last-card suggestion is labelled `WEB?`, never actual. A departure cue is visually offset **symbolically**, not by measured km. A validated past intermediate is pinned to its *static* map dot. Expanded intermediate list hides the folded between-stations caption. UI accessibility retains provenance and unknown-position wording.
- **Data not painted as movement:** page `Last Updated`, HTTP arrival/hash/size, SEO “distance covered,” search-autocomplete data, future white cards, a latest unstable departure, and R139's hypothetical km candidate. Source details **summarises** source status rather than dumping raw HTML/diagnostic detail; the copied feed report includes the R139 distance verdict if the website is selected. The current app does **not export** raw responses for a later full schema audit; a temporary full-body copy exists only in its private on-device HTTP cache, inaccessible from this workspace.
- **Timing:** source state tracks selected website request duration; `TrainActivity.showResponseScore` measures manual tap → completed UI response and displays it. A historical owner 20652 request returned in ~0.4 s; 20689 probes were ~0.5–0.8 s. Neither figure is a guaranteed tap-to-new-km duration. If there is no admitted next-km field, such a duration is undefined.

## 4. Questions already settled versus open, without guesswork

**Settled by evidence:** same-site selected request is undated `trainNo` HTML; `date=2026-10-14` did not change 20689 cards; its page-clock changes need not change station cards; three `distance` hits in that run were promotional; its only observed embedded fetch was search autocomplete; its parsed cards can provide source-labelled station times and named past intermediate reports; static map km is not live km. A phone-app screenshot is not this response.

**Not knowable from the retained data:** every raw tag/field in the full 91-kB 20689 HTML; the current live 12089 HTML field inventory; whether another documented representation on this **same domain** provides dated per-train position; any server-required secret/signature; whether other label formats encode remaining km; a trustworthy live movement sensor behind the website. None should be filled in by extrapolation from code, hashes, fixtures or marketing text. This is a deliberate **unknown**, not an invitation to invent an endpoint or a promise that a query tweak will unlock it.
