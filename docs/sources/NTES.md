# NTES / CRIS enquiry · official-source contract

**Status:** app has a request/parser, and an owner-phone 20689/16227-era diary recorded dated envelopes with scheduled rows and reported minutes; this is not proof of 100% accuracy or a permitted third-party API agreement. `https://enquiry.indianrail.gov.in/mntes/` in the candidate list is a **public UI**, not the app's wire URL. Sources: `remote/NtesWire.kt`, `remote/LiveProvider.kt#NtesProvider`, `remote/NtesMobileFallback.kt`, `remote/NtesRoute.kt`, `ui/LiveViewModel.kt`, [R62](../R62-source-audit.md), [R76](../R76-position-source-evidence.md).

| Layer | What is actually available / used | What is excluded / unknown |
| --- | --- | --- |
| Request | POST `https://enquiry.indianrail.gov.in/crisns/AppServAnd`; plain inner question `service=TrainRunningMob`, `subService=ShowFullRunJson`, selected train and IST-formatted `startDate`, enclosed in `jsonIn` encrypted/integrity-framed body. A separate `GetTrainSchedule` can supply a route; a session-warmed mobile JSON fallback is tried after refusal. UA and content-type are supplied by code; retries/transport path are bounded and device-dependent. | `mntes/` webpage is not the same response. The framing constants in code are not a user credential or evidence of authorized integration; do **not** copy them into documentation/other services, spoof a client or assume changing a signature unlocks a new data field. No genuine current official-client HAR or provider permission has been established. |
| Response envelope / run | Encrypted `jsonIn` or bare JSON, parsed into route rows (e.g. `STNS`), train/run identity and update timestamp; route code/order/endpoints and selected origin day must be verified. Captured owner report for 20689 had 10 scheduled halts, 7 with reported minutes, ~23.9 kB dated replies in ~319–427 ms on that device. | `HTTP 200`, response length, feed update stamp and a `STNS` array do **not** by themselves prove movement. Unknown shape is logged as key structure without values; cache-only reply is refused as a new answer. |
| Row data | Code/name; scheduled ARR/DEP or STA/STD; potentially ATA/ATD or ETA/ETD, platform, delay, cancellation and route km. Parser accepts documented code aliases and marks unsupported fields null; the dated schedule may expand available halts. Fresh **event** minutes in run-matched, ordered rows become source-labelled reported cells, last station event, age and at-stop delay. | STNS `ETA`/`ETD` may be estimates or schedule echoes, not automatic actuals; future/untrusted cells are rejected (`NtesMobileFallback.trustedRows`). Delay-only is not an event. Platform is changeable. Route km is **static station chainage**, not remaining km to the next station; no direct cell-tower/GPS fix is established. |
| UI | NTES selected source shows its own reported stop times, age, last-report badge, projected/symbolic rail states only under their separate gates; next scheduled/estimated label retains provenance. Last known remains labelled on failure. | A later UI refresh or `LUPDT` alone does not move the marker or backfill an arrival. When official feed refuses the phone, fallback is attributed to the actual other source, not silently called NTES. |

**Request flexibility:** train number, date and subservice are known request inputs; schedule and running subservices answer different questions. Probe/adopted transport variants may change how an existing question is carried when an allowed response was demonstrated on that device—not its evidentiary meaning. No supported `remainingKm`, GPS, or satellite/cell fix query is established. The candidate table's “100% Accurate / direct track-circuit signalling” is **not substantiated** by these captures; official provenance does not guarantee an event is current or a coordinate is measured. No IRCTC booking-site request is part of this NTES contract.
