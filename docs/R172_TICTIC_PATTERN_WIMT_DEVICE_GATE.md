# R172 — TicTic-style device acceptance for the selected website

The reference repository `tarungittarun/TicTic` has many focused Actions workflows. Its candidate69 qualification builds APKs and instrumentation, runs a matrix on emulators, retains device screenshots/reports, and distinguishes infrastructure failures from tested behavior. Checktrain02 already had a manual-only broad `e2e.yml` and Android JVM/Robolectric/published-APK acceptance. None of those **required an online, selected `.org.in` website report and painted site clock**; some explicitly allowed a no-report result. The user explicitly requested a focused device run now. Broad E2E stays manual-only.

This round adds `wimt-website-device-acceptance.yml`, which runs only on an explicit `[wimt-device]` test/workflow push or manual dispatch. It builds the app and instrumentation APKs from one commit, boots an online API34 emulator, installs both, enables the diary through the UI, searches for 20652, selects the independent `.org.in` website, and **fails** unless the screen paints a source-qualified past card and website-attributed clock. A browser verification page, HTTP 403, NTES fallback, undocumented `.in` cache, stale/missing run or unbooted emulator cannot pass. It captures before/after/final PNGs and XML hierarchies and an assertion log, with seven-day artifact retention. A bounded report and commit comment avoid raw session/cookie/CDN-ID publication. This is not the Google WIMT phone app or proof of a user's phone connection.

[First device run 42026847014](https://github.com/tarungittarun/Checktrain02/actions/runs/42026847014): **RED**. The APK/test APK compiled and the emulator test executed exactly one method; the UI assertion reported `Website refused request (HTTP 403)` on the selected `.org.in` source and did not show a qualified website past card. Its screenshot/hierarchy artifact was uploaded, but the repository's six-hour Actions artifact janitor subsequently deleted it before the requested PDF could be published; those original screenshots can no longer be recovered. The original host-side parser found no readable opt-in diary, so it incorrectly reported `NO_WEBSITE_NETWORK_ANSWER` and `websiteGetCount=0`; **zero was not evidenced**. [Report-only recovery 42027893268](https://github.com/tarungittarun/Checktrain02/actions/runs/42027893268) pulled the already executed artifact without another site GET and exposed the actual assertion. The report parser is now corrected to distinguish a *visible UI 403 with diary unavailable* from a measured wire count; it must not invent a count or claim a train event. Future runs will include the bounded assertion excerpt automatically.

The first run requested 20652 late in the IST day; its screen said the selected journey had not started by timetable, so even an HTTP 200 would not have been a valid active-run success. The test uses timetable candidates: 20652 at 05–11 IST, 12002 at 12–13 IST, 20651 at 15–19 IST and 16227 at 20–23 IST; outside those windows it fails *before* asking the website. These are dated offline timetable candidates and do not prove a train is actually running or where it is. Those timetable windows are test candidates, not evidence of the train's actual position, and the chosen run must still pass the app's own date/card qualification. [Installed-APK run 42179936690](https://github.com/tarungittarun/Checktrain02/actions/runs/42179936690) selected the midday 12002 candidate and FAILED with a UI-observed independent website HTTP 403. **Correction:** its post-test host screenshot captured the Android launcher, NOT TrackTrain; the PDF previously published from that image was invalid and its release asset has been deleted. The report must never count an after-test home screen as in-app proof. An attempted strict capture at [run 42203043295](https://github.com/tarungittarun/Checktrain02/actions/runs/42203043295) failed *before a website request*: the instrumentation test APK tried to write to its own unwritable data directory. The test now captures in the writable TARGET app directory during instrumentation, fails closed if the screenshots/hierarchies are missing, retrieves them with `adb run-as` and rejects launcher-only images.

[Installed-APK run 42203951014](https://github.com/tarungittarun/Checktrain02/actions/runs/42203951014) built both APKs, launched TrackTrain on an API34 emulator, selected the independent website for the afternoon 20651 candidate and failed the **source-strict** assertion on UI-observed HTTP 403 with no qualified past card. The report gate required both real in-test PNGs plus matching TrackTrain UI hierarchies (including the visible 403) before publishing a [three-page PDF with the actual before/after app screenshots](https://github.com/tarungittarun/Checktrain02/releases/download/latest-apk/wimt-website-device-42203951014.pdf). The PDF was published in the same job before six-hour artifact cleanup. A failed source response is still a RED source verdict, not a data success or Google phone-app feed. No browser spoofing, weak assertion or false green was added. The site controls its refusal; app code cannot make an HTTP 403 into a WIMT report. Keep PR #3 open until permitted access and owner-phone validation; neither emulator evidence nor a green unit/build job substitutes for that acceptance.
