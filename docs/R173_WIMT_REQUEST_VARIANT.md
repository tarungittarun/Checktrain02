# R173 · One honest request variant; source-strict installed-APK gate

**Question:** can the independent `whereismytrain.org.in` website answer a normal TrackTrain request for an English train page when the explicitly chosen source previously showed HTTP 403? The public indexed train links use `/?trainNo=NNNNN`, which is already the app's URL. The only embedded page `fetch('/api/search.php?...')` found in earlier HTML is search autocomplete, **not** a live-running-status feed. Neither an alternate authorized running-status API nor a Google WIMT phone-app feed has been established. A current read-only check of both the home and train pages surfaced browser verification, not usable train cards.

This trial changes **one standard content preference**, `Accept-Language: en-IN,en;q=0.8`, on the selected `.org.in` website request. It keeps `Accept: text/html`, the honest `OpenTrackIndia/1.0` identity, same indexed HTTPS URL, four-second budget, zero HTTP retries and no cached 403 fallback. It does not use cookies, Google-app identifiers, forged Chrome headers, a browser-check solver, redirect hopping, provider IP rotation, or an extra request on a 403. English negotiation could help if an accepted site answer localizes its station-card labels; it is **not** evidence that a CDN block will lift. Local socket/unit/contract tests assert the real wire header and refusal behavior; the separate online source-strict APK emulator gate must still fail on HTTP 403, NTES fallback or unqualified cards. Do not declare the source working just because these offline tests or the APK build pass.

A separate one-time read of the undocumented `whereismytrain.in/cache/live_status` endpoint for 20651 and 06-Nov-2026 returned JSON with `lastUpdateIsoDate` around 17:34 IST, but also filled `actual_arrival_time` for future stops including TLGP at **21:45** while it was only around 17:35 IST, and many entries were marked `source: eta`. Those future values cannot be observed actuals. That endpoint is a distinct Google/Sigmoid web-cache candidate, not the selected `.org.in` website and not a verified Google phone-app interface or authorized automatic feed. It is **not** spliced into TrackTrain's selected website report or its ACTUAL column. The response shows why an HTTP 200/field named `actual` cannot qualify WIMT data by itself.

After the explicitly opted-in installed-app run, record the exact source verdict, screenshots taken *during* the app journey, and whether a real website past-card/clock passed. If the site still refuses, stop experimenting with request identities and ask the website operator for a documented integration/authorized exception, or get an authorized Google WIMT interface.
