# R168 — Can the previously working website source work again?

Research date: 4 November 2026. This is about the **independent `whereismytrain.org.in` website**, the source that previously answered TrackTrain's selected-source Refresh. It is **not** Google's `com.whereismytrain.android` phone-app telemetry, `whereismytrain.in/cache/live_status`, or NTES. No app code or request policy was changed in this research. No new train-status GET, CDN-challenge handling, or owner contact was attempted. PR #3 remains unmerged pending phone acceptance.

`git diff ff03ed4 ef0b7b2` found **no changes** to `PublicPageChecks.kt`, `Http.kt`, `LiveViewModel.kt`, Android manifest or network-security config between the successful R158 and R160 APKs. The URL was `https://whereismytrain.org.in/?trainNo=<train>`; the same Java HTTP transport and Chrome-like User-Agent, `Accept: text/html`, `Cache-Control: no-cache` and `Pragma: no-cache` were used on those builds. R161's initial request used the same UA; later fallback logic did not explain the first 403. Since R162 the app honestly identifies itself, removes those forced cache headers and needless comparisons, makes one GET per explicit check, does not retry 403/429 or serve its old HTTP cache as a fresh site reply, and pauses that host for 15 minutes after refusal. R164 still got 403. **Reverting the APK, reinstating a browser-like UA, or changing the parser cannot be defended as a tested fix.** The exact trigger is unknown; possible website rule/security changes, temporary protection, request-rate history and network reputation remain hypotheses.

Hostinger's [browser-verification guide](https://www.hostinger.com/support/hostinger-cdn-the-browser-verification-page/) describes JavaScript checks and verification cookies; ordinary HTTP clients often cannot complete them. Its [troubleshooting guide](https://www.hostinger.com/support/hostinger-cdn-troubleshooting-website-errors/) says `x-hcdn-request-id` traces a response through the CDN and a 403 is *usually* a security rule, but a response delivered through the CDN may originate from the site. The site owner must isolate the layer; `Server: hcdn` alone is not a rule verdict. Stack Overflow answers proposing a `Mozilla/5.0` header for unrelated Android 403s do not explain this incident: the working and failed APKs already sent the same browser-like header. Do not replay cookies, impersonate browsers, script verification, probe different addresses/IPs, or defeat the challenge.

## The route back to *this same source*

1. **Get the site operator's consent and correlation.** The indexed [contact page](https://whereismytrain.org.in/contact) lists `support@whereismytrain.org.in`, `tech@whereismytrain.org.in` and `business@whereismytrain.org.in`; live access to that page is challenged, so verify contact details before sending. Privately supply one **original unredacted** owner-phone `x-hcdn-request-id` (if present), exact IST/UTC time, `GET https://whereismytrain.org.in/?trainNo=20689`, HTTP 403, and app identity. The prior redacted diary cannot supply the request ID. Ask *both* whether third-party automatic use is permitted and what endpoint, authentication and maximum rate the site supports. One-minute Auto must not be assumed allowed.
2. **Ask that operator to diagnose the refusal, not lower security from our app.** Hostinger's [blocked-legitimate-requests guide](https://www.hostinger.com/support/hostinger-cdn-how-to-fix-blocked-legitimate-requests/) instructs the owner to check the Security level and country/IP traffic-blocking rules; with a request ID, time and URL, Hostinger support can inspect the rule and arrange a precise exception where justified. The operator can isolate CDN versus origin (temporarily disabling CDN under their own control, then re-enabling it). A mobile phone has changing network IPs; a generic phone-IP allowlist is not a robust integration design. Prefer the operator's documented permitted feed/credentialed access or a specifically authorized endpoint/client policy, not a global protection downgrade. An allowed HTML response is not itself permission to republish or proof of station accuracy.
3. **After permission/access, verify end-to-end before claiming recovery.** With the chosen source selected, one deliberate *owner-phone* Refresh should yield the site's actual HTML, matching train and active IST origin run and route, real source-labelled past-card clocks, and an honest event age. A declined/estimated/future clock must stay out of ACTUAL and the train-position marker. Confirm no new GET during a 403/429 pause, one selected-source request before an explicitly named NTES fallback, and Auto at only the operator-approved interval. Preserve the updateable signature and obtain the user's APK acceptance before merging PR #3. A green JVM/build run or a Chrome tab loading the page is not this test.
