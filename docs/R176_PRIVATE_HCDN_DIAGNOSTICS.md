# R176 · Private Hostinger request correlation and normal WebView capabilities

The selected source is the independent `whereismytrain.org.in` website, not Google's WIMT phone app. `Server: hcdn` and an HTTP 403 are **not proof** of which security rule or layer refused the request. The site operator must correlate an original request ID with its own CDN and origin logs; none is invented when the header is absent.

For an opt-in diagnostic capture, enable **Settings → Diagnostic log**, wait until any existing 15-minute refusal pause has ended, then select the website/perform **one** explicit Refresh on the owner's device. Save the log on the device and locate the line tagged `[SITE_REFUSAL_PRIVATE]`. On a main-frame HTTP 403 for the exact five-digit train URL, it records the complete original `x-hcdn-request-id` header value if well-formed, UTC callback time in ISO-8601, and the exact requested URL (including train number). If the header is missing, the line says `<absent>`; malformed/oversized headers say `<invalid-or-oversized>`, not a made-up identifier. No response body, cookie, challenge token, unrelated subresource error, or arbitrary redirected URL enters this receipt. The request ID and journey URL are **private operator-correlation data**: do not paste the raw log into a public issue. The diagnostic collection switch is off by default and the user controls export; ordinary diary entries still redact credential/digest-shaped strings. CI reads any raw diary only transiently and never uploads it or publishes the ID.

Before `WebView.loadUrl`, the selected website now explicitly has JavaScript, DOM Storage and the legacy database setting enabled, and accepts first-party cookies via Android's `CookieManager`. Third-party cookies stay disabled because the train page is first-party; there is no demonstrated need to allow unrelated tracking domains. This is normal WebView configuration, **not** a Hostinger-required guarantee, an approved automated feed, a challenge solver or proof of access. A 403 still ends the request and invokes the existing host-wide pause. A 200 verification page still cannot become a train event. No fake browser headers, copied browser sessions, CDN rule evasion, extra homepage GETs or IP rotation are added.

This release uses the existing stable test signing key and increments versionCode to 98 / R176 so the APK can update in place. Offline tests exercise case-insensitive header lookup, exact receipt/time/URL, absent and malicious headers, opt-in-only collection and preservation of a digest-shaped request ID without weakening redaction of other diary lines. This run did **not** perform a new source-strict website GET or capture a real Hostinger request ID. A green build/test does **not** mean the website now permits the APK.
