# R70 — visible suggestions and a bounded device loop

The API 34 row in R68 booted, but all station/train search flows failed. Reading the shipped layout against `SuggestBox` found a concrete defect: `view_suggest_box.xml` starts `suggestScroll` as `gone`, while `SuggestBox.render()` made **only its child** `suggestPanel` visible. JVM `rowCount > 0` stayed green even though every row was hidden by the parent. R70 toggles the actual scroll container, checks its visibility in Robolectric, and stops selected suggestions from reopening after the programmatic text replacement. The device outcome is still to be measured; the layout bug is not itself proof every flow now passes.

Two station-flow tests also never typed the three-letter query they claimed to test. Those now type it. Settings rejected no invalid endpoint and the previous device test read `state` **after leaving Settings**; invalid addresses now stay in Settings with an explicit correction, the test reads that feedback on the right screen, and a successful cache clear updates a persistent state line rather than only a transient Toast. The search screen initializes its offline-data label before the asynchronous first update so a cold first frame is not blank.

The old default E2E push launched two emulators, built the R8 release APK even when no release row would run, fetched that unused APK into both rows, performed 30,000 random events on API 34 and **another 4,000 after reopening** even for a short smoke, and ran a roughly nine-minute independent-source probe on *every* search/UI patch. A push now runs one required API 34 device row with the full UI suite and offline pass, followed by a 600+600 event smoke. It does not build/download the R8 APK or run the expensive probe unless requested. A main push or explicit `[e2e-full]`/full dispatch still runs API 24, density and R8 release, with coverage and detailed reports. `[probe]` or dispatch runs the source investigation. Core row budget is 30 minutes and job deadline 40; full rows retain 50/65 minutes so they can report before GitHub cancels them. Skipped API 24/release on a branch is **not** evidence those variants pass; require a full sweep before release.

R69 Android compile and JVM checks passed (run `38632789526`); its device workflow was queued when this fix was prepared. R68 device run `38627580569` ended cancelled after its API 34 failures; it cannot be reported green. R70's CI run must be inspected for the actual on-device outcome and JaCoCo diagnosis. These changes do not claim independently verified actual arrival/departure times or on-phone speed.
