# R136 · Repair selected website timeline, not just its badges

## Owner reproduction (19 Oct 2026)

`opentrack-diary-20261019-112912.txt`, 184 lines, screenshots `Screenshot_20261019-112856_TrackTrain.png` and `Screenshot_20261019-112902_TrackTrain.png`: train 20652's selected website returned a network answer within ~0.4 seconds at 11:28:35 and again at 11:28:45. The parser produced **15** past-card rows, last **YPR arrival 11:26**. NTES separately reported **TK departure 10:35**, already 53 minutes old. Despite this, the website selection showed dashes in the right-hand column and no site marker; `LiveViewModel.refresh` logged `failed (comparison); fallback=NTES`. The app was conflating a parser-qualified site report with a failure because its state string was `comparison`. R135's rollback restored the R132 admission gate rather than the previously working site display. The user correctly identified that the frontend-only request did not authorize that loss.

## Restored behaviour and boundaries

- A **network answer with parser-qualified past cards** is usable by the selected website. Manual and opt-in Auto refresh ask the selected website first and **do not switch to NTES** just because its independently verified-actual gate is false. A cache-only body, failed request or no qualifying cards may still fall back. Explicit source selection requests the website again; any retained older site report keeps its original event/page clocks on failure.
- The selected website's **own** past-card stop minutes populate the route's right-hand cells with amber `WEB` labels and website accessibility provenance. Its last supported halt gets a website-attributed train logo and `At … / As on …` when stations are collapsed; a mapped intermediate is displayed on the same leg. The next stop remains a *timetable* value, not an ETA. NTES selection shows only NTES values and restores its independent old TK event. No website minute leaks into NTES.
- The top card gives the last website-published stop and its **event age**; its at-stop delay uses the site's published arrival versus the selected schedule. Positive is red, early green, on-time neutral. It does not claim a present GPS location or that a page-update label marks movement. Source receipts report an unchanged past card as unchanged even if the page clock changes.
- **Preserved R132 safeguards:** the website is not the Google phone app; its page omits the origin run date, so the association is inferred from the *selected active timetable*, not independently certified. `OrgWebsiteStatus` still rejects mismatched train/endpoints, future runs, stale publication clocks, white/future cards, schedule echoes, provisional last-card departures and claimed events later than the site's own publication timestamp. Independent `primaryActuals` remains zero for the website; source evidence logs distinguish site rows from NTES-confirmed data. No client spoofing, hidden API/permission assumption or anti-bot workaround.
