## Source-code comparison, not guesswork

The successful R158 binary maps to commit `ff03ed4` (`app/build.gradle` versionCode 87 / `1.0.84-r158`); R160 is `ef0b7b2` (versionCode 89). `git diff ff03ed4 ef0b7b2` shows UI/layout, battery rendering and version changes, but **no changes** in the website URL/request builder (`PublicPageChecks.kt`), HTTP transport (`Http.kt`), source orchestration (`LiveViewModel.kt`), Android manifest or network-security configuration. The site URL remained `https://whereismytrain.org.in/?trainNo=<five-digit number>`. The request used the same Chrome-like User-Agent override, `Accept: text/html`, `Cache-Control: no-cache`, `Pragma: no-cache`, and the same Java HTTP stack. R158's several responses on 28 Oct were successful even with those headers. No app-side network-path edit in the R158–R160 interval explains the transition. R160 has no later successful/failed phone GET on record.

R161 (`227e1bb`, 1 Nov) changed manual preferred-source retry/fallback and HTTP error reporting **after earlier runner refusals but before the first logged phone refusal**. The R161 request's URL, headers and initial HTTP GET implementation remained as on R158; its source orchestration could alter the *number and timing* of requests. With no phone diary between 28 Oct and 1 Nov, R161 cannot be categorically excluded as a contribution to traffic, but the later requests in the 1 Nov diary cannot have caused its already-failed first GET. R162 (`3d095fb`, 1 Nov) responded by removing Chrome impersonation and forced cache revalidation for this site, limiting requests and not serving stale HTTP cache as a successful website reply. An R162 runner request still got 403. The phone's R162 behavior is unconfirmed without a version-stamped test. Do not retroactively present R162 as the cause of the earlier denial.

## Path through the code

1. `PublicPageChecks.url()` constructs the website URL; `headersFor()` supplies `Accept: text/html` in R162; `Http.tryOnce()` supplies `OpenTrackIndia/1.0` and performs the GET. The pre-R162 builder overrode that identity with a Chrome-like string; it did not run Chrome.
2. `Http.tryOnce()` reads `responseCode` before reading any page; for 403 it immediately returns `Result.Failed(HTTP, "HTTP 403")`. The site parser, HTML station mapping, day inference and table rendering **never see this response**. Changing their fields cannot turn a 403 into website data.
3. Pre-R162, `Http.get()` could attempt a cached body after refusal. The diary distinguished these attempts from `NETWORK_ANSWER`; a cached result is not a fresh report. R162 disallows that fallback for this website and holds a host-wide 15-minute pause after 403/429. An HTTP refusal is not retried over IPv4 or as a dropped socket.
4. Before R162, normal first-load survey could ask the website even when NTES was selected; a manual source selection, refresh, and map-recheck could ask again within seconds. The R161 diary logged seven 403 GETs in roughly 33 seconds. That is a request-design flaw worth correcting regardless of the root cause. R162 narrows unsolicited requests, but cannot force acceptance of a GET.
5. The same phone receives NTES data on the failure screen, so general device connectivity is not the explanation. Chrome showing the train page nearby does **not** show Chrome's response status, cookies, challenge state, origin, or policy; Java HTTP and Chrome are not equivalent sessions.

## Remedy boundary and next evidence

The immediate **permissible app-side correction** was R162's honest identity, single-request pacing, no automatic refusal retry, and truthful cache handling. It was not an access grant; the independent runner still receives 403. It would be false to promise that changing User-Agent, adding browser cookies/headers, rotating networks, automating a browser challenge, or parsing the refusal page will restore sanctioned website data. Those are not proposed. No documented, authorized website feed has been established by the repository investigation. Repository search for the domain returned no match, which does not prove no integration exists.

For a durable automatic website feed, ask the website operator for **documented integration/permission, allowed origin and request limits, and run-date/event semantics**; implement exactly that contract and test that the phone receives HTTP 200 with page bytes and source-correct station rows. Alternatively a user-initiated import of an authorized, user-saved page could be scoped separately, but would not be a live GET or a substitute for consent. Until either path exists, keep WIMT website rows empty on refusal and NTES separately labelled. A version-stamped R162 phone diary with a single selected-source refresh (after any 15-minute pause) would distinguish runner-only denial from phone denial; it would still not reveal the operator's policy. Never merge PR #3 merely because the unit tests pass.
