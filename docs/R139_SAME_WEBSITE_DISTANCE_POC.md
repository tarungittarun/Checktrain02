## In-app bounded POC

`OrgWebsiteDistanceProbe` runs only when the existing `.org.in` parser has a qualifying same-run, non-cached page report. It strips scripts/styles and checks visible HTML for a single explicit `N km to CODE` label. The code must match the **immediately following point** on the independently validated map (or next scheduled halt when no map exists); the reported km must fit the leg on the *same* route-distance axis. A synthetic fixture with past-card ARU, next ANF, 15-km leg and `1 km to ANF` calculates **14/15 = 93.3% schematic fraction**. Missing, multiple, mismatched, out-of-range, script-only and stale-page examples are rejected. This proves extraction/calculation *would* work if the selected website actually supplies an eligible value. It **does not** prove it does. Even a synthetically accepted candidate appears **only in diagnostics**; it cannot set `Act`, move the rail icon or become an automatic live fix before source semantics and on-device updates have been observed.

The POC verdict appears in TrackTrain's **copied feed report** (long-press the provenance badge) when the website is selected. **Source details currently condenses the raw result and does not show the detailed distance verdict**; the earlier claim that it did was incorrect. If the source only supplies stop clocks in the searched format, the copied report says the `N km to CODE` label was absent. No HTML, cookies, identifiers or raw page text are copied to the report. A cached response, fallback to another source or a regressed page cannot supply a new distance candidate. See the [canonical response inventory](sources/WHEREISMYTRAIN_ORG_IN.md) for exactly what is and is not established.

## Refresh-to-screen timing

The existing website HTTP request has a **4-second network budget**, and the UI already measures the manual **Refresh tap → completed screen receipt** with `SystemClock.elapsedRealtime()` and displays that response time. Source details also record the website request duration in milliseconds. A previous owner diary for 20652 measured about **0.4 seconds for the website answer** on that phone/network; this is not a 12089 refresh measurement, a guarantee, or proof that a distance field exists. The added parser makes no network call; it executes synchronously during parsing of the same reply. **A click-to-new-km time cannot currently be measured, because no actual same-website km-to-next claim has been captured.** If the owner refreshes with R139 and shares the copied feed report plus a screenshot of the refresh receipt, we can establish whether the **visible `N km to CODE` form** is present and measure that phone's tap-to-result time. If the diagnostic says absent, it means no eligible label in this exact form was found; an owner-provided page capture would be needed to decide whether a differently formatted or script-carried same-site field exists. No such field may be treated as movement just because the page answered quickly.
