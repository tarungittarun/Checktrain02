# Device-flow incident · 14 October 2026

Two consecutive device runs on a booted API-34 emulator, `38581350183` and `38594195483`, reported zero useful UI flows. The second run's new bounded check annotations identify the *actual common failure*: `no board-at field on the search screen`; the cold test also found neither status nor data chip. The test harness built selectors with `By.res(PKG, "id/fromBox")`, but UIAutomator's two-argument `By.res(package, resourceId)` adds `:id/` internally. The harness was looking for `in.opentrack.india:id/id/fromBox`; all 21 such selectors, including the shared helper, missed the UI. They now pass the bare IDs and a cheap pre-emulator regression check enforces this. This explains the broad *test blindness*, not proof that all app flows work.

The same API-34 trial also found the separate eRail field test received HTTP 200 with zero halts/one unclassified record. The inaccessible raw body does not prove whether it was HTML or identity text. It is not a verified actuals source; the field test logs this as unavailable and asserts such an answer creates **no** reported minutes, instead of treating absence of eRail data as an app failure. Official NTES validation is unchanged. Instrumented tests for the removed Auto/source-card controls were updated to the new manual Refresh and Info dialog.

The old `38533032246` job log/artifact remained inaccessible due redirects to blob storage (`EOF`). The check annotations of `38594195483` supplied the first directly readable class-level exceptions. A subsequent device run is still required to verify the selector fix against a real emulator; JVM renders/compile are not substitutes.
