# R175 · Actual browser-engine navigation for the selected website

The user clarified: a local server simulating a refusal, and a Java `HttpURLConnection` request with browser-looking headers, are **not** the website request they wanted. This change makes TrackTrain's selected independent `whereismytrain.org.in` request a real Android **WebView document navigation** from inside the APK. The app's screen is unchanged; this is not the old external-browser action. A fresh WebView uses its own default User-Agent, TLS/HTTP stack and normal page rendering. No Chrome UA, copied browser cookies, TLS fingerprint impersonation, or fabricated Chrome HAR is supplied. WebView is a browser engine **but is not bit-identical to the owner's Android Chrome**: version, session, IP/network, headers and challenge decisions may differ. An exact Chrome request cannot both be made by Chrome and silently copied into this app's table.

`LiveViewModel` now chooses `WebsiteBrowserRequest.document()` only for the **selected `.org.in` source**, before the existing `PublicPageChecks` train/run/clock parser. Other sources continue on their previous transports. The website browser request validates the exact indexed train URL and five ASCII digits, has a 12-second bound, accepts only the original main-frame URL, rejects main-frame HTTP errors/redirects/network errors, bounds DOM extraction to 1 MB and returns fresh HTML to the existing source-strict parser. No JS bridge or challenge-solving script is injected; the site can refuse WebView as it pleases. The existing host-wide persisted pause after 403/429 still runs before any selected-source request. A 200 challenge, stale/schedule-only card or different train cannot become actual event data. Normal browser subresources may load; the private diary's `try#1` counts the **main document navigation only**, not every resource GET.

The legacy Java HTTP helper wire test and runner `urllib` trial do **not** prove this new browser path. The opt-in mobile-assurance emulator checks the APK's offline refusal/qualification behavior and invalid browser URLs, while the **separate opt-in source-strict online installed-APK workflow** actually navigates the independent website and requires a source-qualified card and painted clock. A failed site test remains red and must not be reclassified as a browser success. Any screenshot/PDF must be captured in-app during instrumentation, not from a post-test launcher. No owner-phone acceptance or provider permission is established by an emulator pass. PR #3 remains open until the user confirms the APK works.
