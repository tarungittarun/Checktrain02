## Same-screen comparison checklist for the owner's phone

Capture the site's page clock and OpenTrack's copied diary at approximately the same time; site fields have already changed *after* a card was coloured green. A pass is not "the train was really here" but "the app displayed exactly the selected website's attributed claim without changing static data":

1. Origin run: OpenTrack says 14 Oct 2026; the website has no displayed origin date. The app must state **inferred**, not claim the page identified that run. A different selected run must not acquire these rows.
2. Station and sequence: only website past-marked, route-matching cards with paired first/grey clocks can become `Web`; white upcoming cards never become `Act` or `Web` by clock coincidence.
3. Arrival and departure are independent cells. A future site departure cannot appear as a past departure, and an arrival-only card cannot fabricate departure. Compare each `Web` cell with the site's *first* clock and `Sch` with the site's grey clock and the static table.
4. Website PF is attributed `web pf`, not an official platform; future PF does not move into the live row. A delay label need not equal departure lateness and is not upgraded to an observed event.
5. Headline is the site's **last past stop**, not a measured moving location. Its kilometre is from the static route, not phone GPS. The next and intermediate stops remain scheduled; no source-derived ETA is invented for them.
6. A page clock more than five minutes old, an HTTP cache fallback, wrong train/endpoints, or no qualifying pair must yield a static table with a visible reason. A fast HTTP 200 on its own is not validation.
