# R108 · train 16205 website-event regression and source markers

## The 17:09 → 17:12 reproduction

The owner's screenshots showed the `.org.in` page moving from an intermediate BEI claim (17:03) to a later BDVT arrival claim (17:10), while the app's website-selected train icon jumped **back** to KMSI (16:21). A read-only runner capture for train 16205 at ~17:20 IST (research run [38730472508](https://github.com/tarungittarun/Checktrain02/actions/runs/38730472508)) found a **blue** SMET card with arrival **16:48** beside scheduled **16:45**, and a *single* 16:50 departure clock. BDVT and MSS cards were green and later. SMET remained blue when later cards were green. The parser previously accepted green cards only, so it could discard a reached blue station and anchor at the earlier KMSI. The website does not supply a trustworthy dated run ID or onboard GPS. Its page-update clock is not a station event.

The new fixture models the owner's BEI → BDVT progression and uses the captured blue/two-clock SMET arrival with single-clock departure. The BDVT blue class in the 17:12 fixture is a safety case, **not** a claimed historical HTML capture. There is no independent evidence that any of the website's first clocks are railway-confirmed actuals.

## Qualification and display rules

- A blue card **alone** is not evidence. It needs a distinct, schedule-paired arrival already in the past, on the selected train's timetable and active inferred origin run. A white/upcoming card, lone clock, unchanged schedule clock or future time does not become a reported event. Green cards retain their existing rules. The last card's departure remains provisional if the site may keep moving it; a page refresh does not settle it.
- Within one selected train/run screen, a later website reply cannot replace a reached station with one behind it in **validated route order** (static map km breaks ties between points in the same leg; it is not compared against a different timetable km axis). The progress floor remembers the reported station rather than a numeric index, so it is recalculated if a longer dated route loads with earlier halts. A previous report can remain visible only until its *original* page clock reaches five minutes; after that an inconsistent page yields **unknown position**, never a freshly stamped old event. An unavailable selected source follows the existing selected-first / explicitly labelled fallback chain.
- A source-reported timed halt (NTES, erail or a validated mirror) gets a blue locomotive pinned at **0%** of the next scheduled leg, with its source name, reported event age and the disclaimer that its between-stop position is unknown. A validated `.org.in` stop or intermediate is amber and source-labelled; the latter uses the map distance of the *named station*, not inferred movement after it. WIMT web-cache distances remain explicitly unverified. A fresh same-run RailYatri station/status claim gets an amber, untimed pin, not an invented Act or passage time. Sources without qualifying position data get no moving icon.
- Intermediate points keep route order and proportionate **static** km ticks; crowded legs retain all ticks and accessible point codes while suppressing only overlapping visual labels. The expandable station table names the points without inventing arrival/departure times.
- The primary age line and icon age recalculate from the source's **stop/event timestamp** every 30 seconds without making a network request or moving the icon. Multiple refreshes in the same minute may properly show the same rounded minute; a changing page-update timestamp must not reset the event age. The site page clock remains separately labelled as a non-event.
