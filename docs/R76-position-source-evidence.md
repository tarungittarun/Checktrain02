# 16227 · 15 Oct 2026 · actual-position-only investigation

The owner's 03:07–03:10 IST phone diary for the **14 Oct origin run** is the primary evidence. NTES returned 29 scheduled halts and reported minutes twice in under a second; after a 6.5-second timeout the screen wrongly reverted to the bundled 11-halt SBC→SMET route instead of the dated 29-halt MYS→TLGP route. The next NTES request succeeded in 815 ms and reported an 80-minute delay at the last halt, Arsikere. **It did not report a moving GPS coordinate between Arsikere and Birur.** A time/distance interpolation between those stops is not an actual location at 03:10.

The two fallback failures had different causes: `OfficialRunCache.decode` disallowed real one-character station code `Y`, discarding the saved 29-halt official run; `RailRepository.live` preferred the bundled 11-halt timetable to the already-validated, saved 29-halt schedule. Both are corrected with a one-character-code regression test. On a timeout, the full dated schedule remains if its run/span checks pass; a saved official report is explicitly *last-known*, never current.

The tracking screen now prints the **last reported halt/event** and states that the position since that event is unknown. Its progress is pinned to that halt's *scheduled km*, not a fabricated moving km. The proportional interpolated train icon and future delay-propagated times are hidden in the position-only screen; future rows stay scheduled. Historical reported stop times remain labelled `Act` (they are historical observations, not remaining-leg forecasts). The next-stop heading gives a scheduled time, not an ETA. No page result, static kilometer point, or projected minute becomes a moving-position claim.

## Five public candidate lanes tested/investigated, **not** five verified position feeds

The bounded GitHub Actions source trial interrogates runningstatus.in, ConfirmTkt, eRail, RailYatri and the **WIMT web cache** (not the WIMT phone app). Its findings are posted to the trial commit. Direct official NTES is the separate baseline proven on the owner's phone. The first three trial URLs, time limits and observation guard live in `tools/ci/probe_position_feeds.py`; the other two have their own scripts. An HTTP 200 or a matching date *mentioned* somewhere on the page is not enough: a candidate must match the **origin run**, expose a past observation/event timestamp, clear freshness checks and avoid schedule/ETA echoes before it may locate the train. A website wrapping NTES is not independent NTES corroboration. Do not count a source as usable actual position simply because it has a name or answers fast.

## R79–R80 controlled WIMT check (14 Oct origin run, train 16227)

R79 source trial `38645547053` compared two public cache `appVersion` parameters at ~03:38 IST: both returned `BLKR`, `338.285 km`; an 18-second repeat stayed at precisely that point while the **root** `lastUpdateIsoDate` advanced. The current BLKR row carried `actual_arrival_tm` 03:21 but no `updated_at`, and its `actual_departure_tm` was 02:33, *before* arrival. In the same window RailYatri returned `DRU`, 348 km and identified its upstream as `mntes`. Neither is a proof of the phone-app's position: the repeating root clock is a response clock, not observed movement, and RailYatri isn't an independent fifth feed.

R80's manual, **web-cache-only** candidate gate requires the origin date and endpoints, a `curStn` row that agrees with the root and is not marked ETA, its own arrival event no more than 10 minutes old, a coherent departure if one exists, a root response clock no more than two minutes old, and a route distance strictly between independently scheduled adjacent halts. If the gate passes, the screen displays a **WIMT web position candidate** with the row event time and km; all stop minutes in that selected view remain *static schedule*, not WIMT `Act`. This test does **not** make a phone-app API or measured GPS fix available. The actual BLKR observation at 03:39 fails **both** the event-age and inverted-departure gates and will not locate the train. The manually selected source reports the rejection rather than silently replacing NTES. When a candidate passes, a labelled amber marker scales its web-cache km onto the independently scheduled halt-to-halt leg, with static intermediate map points; that scaling is **not** measured GPS or proof that an intermediate station was passed. Manual Refresh rechecks the selected WIMT web source as well as NTES; a refreshed root clock alone still cannot revive a stale row event.

## R84: user-shared browser page is a different service

The owner's 04:14 IST screenshot is from **[whereismytrain.org.in](https://whereismytrain.org.in/?trainNo=16227)**, not Google's `whereismytrain.in` web cache or WIMT Android app. We tested that exact URL in a bounded [read-only Actions trial](https://github.com/tarungittarun/Checktrain02/actions/runs/38649946452) on 15 Oct around 04:17 IST. HTML was server-rendered in **0.5 s**, with RRB 03:37/03:43, TKE 04:02/04:05 and BDVT **04:20** (still in the future at 04:17). Its sole request parameter was `trainNo=16227`: **no origin run date appeared in the URL or visible page**, nor a separate event-update timestamp alongside these station times. A repeat after 12 seconds preserved all four station-row excerpts exactly while `Last Updated` advanced 04:17:28→04:17:43 and the top delay changed from `1min Late` to `On Time`. This browser clock alone cannot validate movement, a stop Act or the icon's position. The site's own [FAQ](https://whereismytrain.org.in/) says it uses IRCTC/NTES data, so its fast UI does not establish a fifth independent source.

At the same time, the dated `whereismytrain.in` cache reported RRB **03:39/03:43** and TKE **04:06 arrival with 03:45 departure** (internally inverted); its root distance changed **377.785→379.460 km in 18 seconds** despite no changed TKE row event, an apparent speed over 300 km/h. The cache's root clock/distance thus cannot safely be treated as an observed GPS fix. RailYatri's dated API said upstream `ntes`, current station TKE, RRB 03:38/03:40 and a *projected* BDVT ETA 04:40. These three renderings do not agree on observed minutes; they cannot mutually certify `Act`. Keep future rows scheduled except the next-stop estimate when its provenance is established; never copy BDVT 04:20 or later browser numbers as historical actuals. The R83 APK deliberately does not promote this newly supplied site into its position or Act feed. `tools/ci/probe_browser_train_page.py` keeps a bounded repeatable check for later evidence.

The trial may expose a useful new schema; no new *verified* position provider is promoted without independent same-run validation of past events and position freshness. Third-party undocumented endpoints or APIs requiring keys/permission cannot be treated as reliable authorized integration by relabeling them. **At present five verified independently usable live-position sources are not established.** [Official WIMT help](https://support.google.com/whereismytrain/answer/16330184?hl=en) documents phone tracking, but no supported programmatic position feed. Its [Play listing](https://play.google.com/store/apps/details?id=com.whereismytrain.android&hl=en_IN) lists `feedback@whereismytrain.in`; no call or email was made by this agent. A request for an authorized, dated per-train location/share integration and provenance documentation would be the appropriate next contact, not reverse-engineering a phone-only cell-location path.

## R86: named links become explicit, on-demand in-app checks

In response to the request to integrate the shared links, the source dropdown now also contains **RailYatri (NTES relay)**, **ixigo page**, and **whereismytrain.org.in (website)** alongside the existing direct NTES, ConfirmTkt and separate `.in` web-cache selection. A tap actually issues a bounded request even if NTES already succeeded. The top of the screen displays the returned origin date or lack thereof, visible run status, RailYatri upstream and station claim/update clock when available, request failure/cache age, and measured check latency; Info retains the full result. Selecting them never copies HTML timetable/ETA times into Act or changes the train marker. An NTES result remains visibly labelled as the table's source; a failed alternate check does not erase it.

The RailYatri request chooses the **specific origin-day offset**, not the page's default Today: its JSON reports `train_start_date`, `data_from`, `current_station_code`, `status`, and `update_time`. A matching fresh run can produce a **textual station claim** only. Prior dated trial recorded `data_from: ntes` for 16227; this is a relay, **not independent GPS**. The route's `previous_stations` ETA/ETD fields were not demonstrated to be observed events (the page even calls some future rows "Departed"); they are never promoted. The ixigo page has no origin date in its requested URL; if its visible selected date is wrong, that mismatch is explicit. `.org.in` has only `trainNo` in its URL and lacked a visible origin-run identity or event-level time in the 15 Oct test, so it is comparison only, not the Google phone app. A cached HTTP response is always labelled stale, not a new observation. Unit fixtures cover previous-origin selection, wrong run/number, stale/future clocks, page script pollution and absent date. These manual checks improve **inspectability**, not the count of verified independent live-position feeds; that count remains below five until evidence changes.
