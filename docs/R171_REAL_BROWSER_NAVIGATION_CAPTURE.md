# R171 — what we actually captured before, and one Chrome navigation trial

The older `tools/ci/probe_browser_train_page.py` was misleadingly named: it used **Python urllib with a Chrome-like User-Agent**, not Chrome. The earlier website pages and R158 app diaries captured HTML returned to HTTP clients, not the user's browser network trace. The 5 Nov owner-phone diary's `[BROWSER]` entry was `runningstatus.in`, **not** `.org.in`. I was wrong to imply that the previous code had already captured an actual Chrome request on the owner's phone.

`browser_request_capture.py` uses a real Chrome binary on a **GitHub Actions runner** and Chrome performance/DevTools events, making one navigation to the independently operated `https://whereismytrain.org.in/?trainNo=20652`. The job is opt-in via `[browser-capture]` in the commit message; it is not run on normal APK pushes or repeated after a refusal. It records only the first document request's method, status, whether `hcdn` and `x-hcdn-request-id` appear, and whether the page title is the browser-verification page. It never prints raw DevTools events, header values, cookies, request IDs, response HTML or session material, nor does it automate a challenge, replay a browser session, or alter TrackTrain's selected-source implementation. Offline fixtures test URL validation and output redaction. The first runner capture passed, but this sandbox's GitHub log-host request returned EOF, so its **actual status was unreadable here**. A second explicitly opted-in navigation publishes the bounded result as a commit comment through the GitHub API; the first success alone is not interpreted as a website success. Even HTTP 200 is only a **page-level** answer, never a verified dated train event.

A runner Chrome request differs from **the owner's actual installed browser** in IP address, browser build and device session. This diagnostic can test whether a genuine browser on that runner reaches the independent website, but it cannot establish why the owner's app was blocked, permission to integrate the site, or access to Google's WIMT phone-app feed. The proper comparison for the owner's browser still requires a consented on-device browser trace or site-operator logs. No APK change is justified by merely copying browser headers or trying to hide the client.
