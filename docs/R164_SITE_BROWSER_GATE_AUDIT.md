# R164 · Browser-check evidence and the authorized recovery path

## The request we shipped, versus a browser

The 28 Oct phone diary on R158 (`ff03ed4`) contains a real 108,395-character `.org.in` network response for train 20652. The first available phone 403 was 1 Nov on R161 (`f482814`), then R163 still received 403 on **2 Nov, 00:10:35 (16227)** and **11:41:06 (20652)**. This is not a single train number, NTES outage, parser failure or HTTP-cache illusion. No diary covers the precise onset. Between R158 and R160 the website URL builder, headers, GET transport, Android network settings and source orchestration did not change. R161 altered refresh/fallback timing but not the initial GET or its browser-like User-Agent; it cannot explain the first 403 by a new User-Agent. R162 removed the misleading Chrome User-Agent, forced no-cache headers and repeated probes. The phone still got 403 on R163. Chrome showing a page is not a record of what code, cookies, security checks, TLS or origin the browser used.

A **single read-only independent fetch** of `https://whereismytrain.org.in/` and its `robots.txt` on 2 Nov returned the title **“Checking your browser before accessing. Just a moment...”**, not site train data. The earlier bounded GitHub runner GET returned HTTP 403 with `Server: hcdn`, HTML, 5,768 bytes and a sanitized `challenge` marker in the body. These observations strongly support a browser-verification gate affecting automated clients, but do not prove the exact CDN configuration, trigger or IP rule for the owner's phone. [Hostinger's own browser-verification documentation](https://www.hostinger.com/support/hostinger-cdn-the-browser-verification-page/) explains that such pages run a JavaScript/browser check and issue a verification cookie to visitors who pass; ordinary HTTP clients may remain on the challenge page. [Its Under Attack mode documentation](https://www.hostinger.com/support/8512979-hostinger-cdn-the-under-attack-mode/) quotes the exact displayed phrase. This does **not** prove that mode was enabled on this specific domain.

**Why a copied browser header is not a fix:** the successful R158 and failed R161 Java GETs already sent the *same* Chrome-like User-Agent, but Java HTTP was never Chrome. R162's honest identity still got 403. Replaying browser cookies, scripting the challenge, disguising TLS fingerprints or automating a WebView solely to get around the refusal would evade the site's access control; it is not a permitted app fix and cannot be represented as authorized data. The `.org.in` site and Google's `whereismytrain.in` phone app are separate. Neither a website workaround nor the unrelated `.in` experimental cache becomes phone-app telemetry.

## App-side changes made now

R164 makes **no extra request** and does not alter GET headers or retry policy. On an actual `.org.in` 403/429, it records only status, whether `Server` is `hcdn`, a bounded alphanumeric `x-hcdn-request-id` if provided, and numeric `Retry-After`. It never saves the challenge body, cookies, token, browser fingerprint, full URL or query string. It cannot reclassify the refusal as a train report. This equips a phone diary with the correlation ID the site's operator can use to identify and, if appropriate, approve a legitimate app client's request. Source-labelled NTES and refusal pacing remain unchanged. JVM tests check the allowlist and hostile-header rejection; CI/phone results are separate gates.

## Site-owner action that can actually restore an authorized GET

The independent `.org.in` site's [contact page](https://whereismytrain.org.in/contact) advertises `support@whereismytrain.org.in` and `business@whereismytrain.org.in`. This is **not** Google's phone-app support. No message has been sent on the owner's behalf. [Hostinger's blocked-legitimate-requests guide](https://www.hostinger.com/support/hostinger-cdn-how-to-fix-blocked-legitimate-requests/) asks for the exact method/URL, timestamp and `x-hcdn-request-id`; the site owner can review its security level, blocked-bot, country/IP rules or request a precise exception from Hostinger support. The owner of *that website*, not this Android app, controls its CDN. An integration agreement should also establish that app data use is permitted, request limits, stable dated run identity and station-event semantics; restoring HTTP 200 alone would not prove current location or actuals.
